Обёртки DEK (`wrapDek`) — без AAD: у каждой свой KEK (пароль, ключ восстановления, PRF, код), подменить одну другой нельзя. |
| Открытый текст не попадает в IndexedDB, localStorage, сеть | ✓ | IndexedDB: шарды, каталог, фото, токен, обёртки — шифротекст; открыто только `vault.json` (по ТЗ) и служебное без данных клиентов: id устройства, ключ устройства (`CryptoKey`), ревизии и имена файлов, очереди id, отметки времени. localStorage/sessionStorage — только одноразовые `state` и `verifier` входа в Яндекс, стираются после возврата. Сеть: `vault.json` и шифротекст (`StorageAdapter.write`), `fetch` — только в `sync/*Adapter*` и `auth/`. Открытая выгрузка (CSV, архив с фото) — только по действию мастера, с предупреждением. Таблицы этапа 1 (`dev*`) читаются один раз для переноса и стираются. |
| Ключи неизвлекаемые, после блокировки удаляются | ✓ с оговоркой | Рабочий DEK — неизвлекаемый `CryptoKey` (вход паролем, ключом восстановления, Face ID, кодом; второе устройство; ключ копии другого хранилища). Блокировка: `endSession`, расшифрованные шарды забываются (`forgetDecrypted`), адреса фото отзываются, шторки и просмотр закрываются, данные экрана очищаются. **Оговорка:** извлекаемый DEK живёт в памяти при смене пароля (мгновенно) и при настройке быстрого входа — до 3 минут между вводом пароля и нажатием «Включить Face ID» (Safari показывает Face ID только по нажатию); стирается при использовании, по сроку и при блокировке (`app/security.ts`). |
| Ошибки расшифровки не глотаются молча | ✓ после исправления | База на устройстве не открылась — экран «Не удалось открыть данные». Файл на Диске подменён или повреждён — «Файл на Диске повреждён… синхронизация остановлена». **Исправлено в ревью:** фото, которое не расшифровалось (на устройстве или пришло подменённым с Диска), раньше выглядело как пустая плашка — теперь помечено значком «Фото не открывается: файл повреждён». |

## Что ещё посмотрели

- **Параметры:** AES-256-GCM, тег 16 байт; PBKDF2-SHA256 600 000 итераций, соль 16 байт, параметры в `vault.json`; ключ восстановления 32 байта → HKDF-SHA256; Face ID — PRF-секрет 32 байта → HKDF; код — PBKDF2 600 000 + обёртка ключом устройства, 5 попыток (попытка считается до проверки).
- **Подмена и откат:** ревизия в AAD и в заголовке файла; каталог ниже виденного — `RollbackError`. Перескок ревизии каталога на 1000 при недоступном каталоге (обход сбоя Яндекса) откатом не считается — ревизия растёт.
- **Чужой `vault.json`:** новый заголовок с Диска принимается, только если его проверочная строка открывается текущим ключом.
- **Вставка HTML:** `dangerouslySetInnerHTML` — только для своих значков и логотипа (константы в коде).
- **Логи:** `console.error` пишет только имя ошибки; паролей, ключей, токенов и данных в логах нет. Подробности синхронизации — имя сервера и тип ошибки, без ссылок (в ссылке скачивания Диска есть номер аккаунта).
- **CSP:** без `unsafe-inline` и `unsafe-eval`, внешних скриптов нет; `connect-src` — только хосты Яндекса.

## Принятые риски

- Код из 6 цифр слабее пароля: при копировании всего профиля браузера вместе с ключом устройства его можно перебрать. В интерфейсе об этом сказано.
- Подмена JS на хостинге (GitHub Pages) полностью не решается — общее ограничение веб-приложений (SPEC §5.5).
- Ключ восстановления, скопированный кнопкой «Скопировать», остаётся в буфере обмена, пока его не перезапишут.
- Порча `vault.json` на Диске человеком с доступом к аккаунту Яндекса может помешать входу на новом устройстве — это тот же уровень угрозы, что и удаление файлов; устройства с хранилищем продолжают работать.
