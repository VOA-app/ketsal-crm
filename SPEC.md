> **Эталон экранов и поведения — прототип:** `prototype/index.html`, исходники логики — `prototype/src/js/`.
> Прежнее рабочее название — «Тайник». Документ написан так, чтобы по нему вести разработку в Claude Code поэтапно (§12).

## 1. Что это

**Приложение для учёта клиентов мастера перманентного макияжа и камуфляжа** студии «Кетсаль» на iPhone, в виде веб‑приложения (PWA). Хранит карты клиентов, процедуры с материалами, фото «до / сразу после / через месяц», анкету здоровья и согласия, напоминает о коррекции и обновлении, ведёт расходники и подарочные сертификаты. Все данные шифруются на устройстве и синхронизируются через Яндекс Диск салона.

Возможности v1 (все есть в прототипе):

- **Карты клиентов.** Номер карты присваивается сам, начиная с № 1. Поиск по имени, любому фрагменту телефона (`8 917…`, `+7(917)…`, `45-67`) и номеру карты. Метки, источник, мессенджер, дата рождения, фото для узнавания, заметки.
- **Процедуры.** Услуга из прайса (цена подставляется), тип визита, зона и техника, анестезия первичная и вторичная, пигменты со смесью, долей и партией, иглы, фото трёх стадий, заживление, стоимость, скидка в % или ₽ с причиной, способ оплаты (в том числе сертификат), статус, работа на модели с курсом, примечание.
- **«Повторить как в прошлый раз».** Новая процедура заполняется материалами прошлой процедуры в этой зоне, партии подставляются действующие.
- **Предупреждения при записи процедуры** (§4.4).
- **Напоминания:** коррекция, обновление, дни рождения, «давно не были», «без согласия». Текст сообщения по шаблону копируется, мастер отправляет его вручную; клиентка помечается «напомнили».
- **Журнал процедур** с итогами за период, **справочники**, **отчёты**, **расходники**, **подарочные сертификаты**, **печать и PDF карты**.
- **Синхронизация** через Яндекс Диск салона между iPhone и компьютером.
- **Сквозное шифрование (E2E):** всё шифруется на устройстве. Яндекс видит только зашифрованные файлы.
- **Экспорт:** зашифрованная копия одним файлом, открытая выгрузка CSV.
- **Бесплатно:** хостинг статики (GitHub Pages) + Яндекс Диск салона. Серверов, которыми нужно управлять, нет.
- **Российские сервисы для данных:** данные хранятся только на Яндекс Диске. На хостинге лежат только файлы самого приложения.

### 1.2. Что не входит в v1 (non-goals)

- **Несколько пользователей, роли и права.** Работает один мастер (решено). Несколько своих устройств — да, по одному мастер‑паролю. Совместный доступ — §13.
- **Онлайн‑запись и расписание.** Запись идёт в YCLIENTS. Интеграция — §13.
- **Импорт старой базы.** Базы нет (решено), нумерация карт начинается с № 1.
- **Конструктор коллекций и полей.** Модель данных фиксированная (решено 25.09.2026, §3.1). Мастер сам меняет только списки вариантов (§4.3).
- Рассылки и отправка сообщений из приложения: только копирование текста.
- Публикация в App Store, серверный поиск, видео в записях.

### 1.3. Персональные данные (152‑ФЗ): требования к продукту

Бланки согласий подготовлены юристом и есть у салона. Уведомление Роскомнадзора и политика обработки — зона ответственности салона.

| Требование | Как реализуем |
|---|---|
| Данные хранятся в РФ | Только Яндекс Диск; хостинг кода (GitHub Pages) данных не содержит |
| Защита данных | E2E‑шифрование (§5), автоблокировка, никаких данных в логах |

| Анкета здоровья | Включена (решено): отметки (§4.2), аллергии, препараты, другое, дата заполнения. Скрыта в списках и таблицах, в карте — под кнопкой «Показать». В открытый экспорт — только по отдельной галочке |

| Право на доступ | Печать / PDF карты клиента (с данными о здоровье — по галочке) |
| Журнал действий | Не нужен в v1: работает один мастер |
| Фото без лишнего | EXIF и GPS удаляются всегда (§8) |

### 3.1. Ключевые принципы

1. **Открытый текст никогда не покидает устройство.** В сеть и в IndexedDB попадает только шифротекст. Исключение — служебный заголовок `vault.json` без секретов.
2. **Offline‑first.** Любое действие сначала применяется локально, синхронизация идёт в фоне. Приложение полностью работает без сети.
3. **Хранилище — это адаптер.** Интерфейс `StorageAdapter` позволяет заменить Яндекс Диск на Yandex Object Storage, WebDAV или мок в тестах без переписывания логики.
4. **Предметная модель фиксированная, слой хранения — универсальный.** Типы клиента, процедуры и справочников описаны в `domain/` (§4.2). Хранение, шифрование и синхронизация работают с «конвертами» записей (§4.1) и не знают предметной области. То, что мастер меняет сам, — списки вариантов (§4.3).
5. **Версионирование всего.** У формата хранилища, у KDF‑параметров и у схемы записей есть номера версий и миграции.

## 4. Модель данных

### 4.1. Конверт записи (то, что хранится и синхронизируется)

```ts
type ID = string;           // ULID: сортируется по времени, генерируется на клиенте
type HLC = string;          // Hybrid Logical Clock: "000017f3a2b4c-0003-<deviceId>"
type Kind = 'client' | 'procedure' | 'service' | 'pigment' | 'needle'
          | 'anesthetic' | 'zone' | 'course' | 'certificate' | 'expense';

interface RecordEnvelope<T = unknown> {
  id: ID;
  kind: Kind;
  v: T;                                   // поля записи (§4.2)
  createdAt: string;                      // ISO
  updatedAt: HLC;
  fieldUpdatedAt: Record<string, HLC>;    // для пополевого слияния (ключи — поля верхнего уровня v)
  deleted?: boolean;                      // tombstone
  purged?: boolean;                       // полное удаление клиента (§1.3, §7.1): без v
}
```

Настройки и списки вариантов (`Settings`, `Lists`) лежат в каталоге (`catalog.enc`) и сливаются так же, пополевно.

### 4.3. Стартовые данные и списки

- **Зоны и техники** — как в прототипе (`prototype/src/js/02-const.js`, `DEFAULT_ZONES`): брови, губы, межресничка (перманент, с обновлением); под глазами, шрамы и рубцы, ареолы, стрии, кожа головы, витилиго и пятна (камуфляж; обновление у ареол и кожи головы).
- **Списки вариантов** (редактируются в настройках): источники, метки, причины скидок, категории расходников — как в прототипе (`defaultLists`).
- **Услуги, пигменты, иглы, анестетики, курсы** — пустые, мастер заполняет в «Справочниках». Для разработки и e2e — демо‑набор из прототипа (включается только в dev‑сборке).
- **Шаблоны сообщений** — как в прототипе (`defaultSettings().templates`).

### 4.4. Правила предметной области

Эталонная реализация — `prototype/src/js/05-domain.js` (перенести в `domain/` с тестами).

**Итоги по клиентке** считаются по процедурам со статусом «состоялась»: визиты, потрачено (сумма итогов), скидки, первый и последний визит, зоны.

**Итог процедуры:** `price − скидка`, где скидка в % = `round(price × %/100)` (не больше 100 %), в ₽ — не больше цены. Неявки и отмены в выручку не входят.

**Напоминания** (по каждой зоне, где были процедуры, кроме зоны, где последней было удаление):
- *Коррекция:* последняя первичная или перекрытие без последующей коррекции/обновления. От `corrFrom − 7` дней — «скоро», в окне `corrFrom…corrTo` — «пора», до `corrTo + 60` — «просрочена». Позже — перестаёт напоминать.
- *Обновление:* только для зон с `update = true`; с последней процедуры в зоне прошло от `updFrom` месяцев (после `updTo` — «просрочено») и меньше `lostAfter`; не показывается, пока ждёт коррекция.
- *Дни рождения:* ближайшие 30 дней (29 февраля → 28-е в невисокосный год).
- *Давно не были:* последний визит ≥ `lostAfter` месяцев назад.
- *Без согласия:* нет согласия на ПД или есть данные о здоровье без согласия на них.
- Ключи напоминаний: `corr:<procId>`, `upd:<procId>`, `bday:<дата>`, `lost:<procId>`. Отметка «напомнили» опускает клиентку вниз списка на 14 дней.
- Значок на вкладке «Клиенты» — число коррекций в окне или просроченных, о которых не напомнили.

**Предупреждения в форме процедуры** (важные требуют подтверждения при сохранении):
- важно: аллергия из анкеты совпадает с действующим веществом выбранной анестезии; отметка анкеты, привязанная к зоне (герпес — губы); партия пигмента просрочена на дату процедуры; была реакция на этот пигмент (заживление «Реакция на пигмент»);
- обычные: анкета не заполнена или старше 12 месяцев; общие отметки анкеты; принимает препараты; нет согласия на процедуру, на ПД или на данные о здоровье.

**«Повторить как в прошлый раз»:** берётся последняя состоявшаяся процедура в зоне (не удаление). Копируются зона, техника, анестезия, иглы, пигменты с долями; партия — первая действующая из справочника. Тип — коррекция, если коррекция ещё ждёт, иначе обновление; услуга — первая активная этого типа для зоны, цена из прайса. Для коррекции форма показывает «Как зажила процедура …» и записывает заживление в ту процедуру.

**Сертификат:** при оплате сертификатом и статусе «состоялась» он становится использованным (`usedProcId`, `usedAt`); при смене способа оплаты или удалении процедуры — освобождается. Статусы: действует / использован / срок истёк.

**Поиск:** строка из цифр и `+()-№.` — номер карты (точно) или фрагмент телефона от 3 цифр (ведущая 8 → 7); иначе — все слова в фамилии, имени, отчестве или нике (ё = е).

**Отчёты за месяц или год:** выручка и сравнение с прошлым периодом, средний чек, скидки, новые клиенты, неявки, сертификаты (продано, оплачено), расходники и «выручка минус расходники», выручка по месяцам (12 столбцов + таблица), разрезы по услугам, зонам, типам визитов, пигментам, причинам скидок, источникам новых клиентов, способам оплаты, моделям по курсам, расходникам по категориям.

### 4.5. Локальная БД (IndexedDB, Dexie)

В IndexedDB тоже **только шифротекст**, чтобы при доступе к файловой системе телефона или компьютера данные оставались закрытыми.

| Таблица | Ключ | Содержимое |
|---|---|---|
| `meta` | key | `vaultHeader` (копия vault.json), `deviceId`, `lastSync`, зашифрованный OAuth‑токен, настройки быстрой разблокировки |
| `shards` | shardId (0..15) | `{ rev, ciphertext }`: шард записей |
| `catalog` | 'catalog' | `{ rev, ciphertext }`: настройки, списки, ревизии шардов |
| `blobs` | blobId | `{ ciphertext, kind: 'thumb'|'photo', synced: bool }` |
| `outbox` | autoinc | очередь изменений для отправки |

При разблокировке шарды расшифровываются в память, строится индекс для поиска и фильтров. Для базы до ~10 000 записей это быстро.

**Шардирование:** запись попадает в шард `hash(recordId) mod 16`. При изменении одной записи перезаливается ~1/16 данных, и при этом на Диске нет тысяч мелких файлов.

## 5. Криптография

### 5.1. Иерархия ключей

```
Мастер‑пароль ──PBKDF2-SHA256 (600 000 итераций, соль 16 байт)──► KEK_pw ─┐
                                                                        ├─ wrap(DEK)
Ключ восстановления (32 случайных байта, показывается 1 раз) ──HKDF──► KEK_rc ─┘

DEK (Data Encryption Key) — случайный AES-256-GCM, генерируется 1 раз при создании хранилища.
Шифрует ВСЁ: каталог, шарды, фото, превью, токен.
```

- **Смена пароля** перешифровывает только обёртку DEK, данные не трогаются.
- **Ключ восстановления** — второй способ развернуть DEK. Показывается при создании группами по 4 символа, без путающихся символов, с кнопками «Скопировать» / «Сохранить в Файлы»; при создании проверяется ввод 4 случайных символов.
- **Параметры KDF хранятся в `vault.json`** с номером версии, чтобы потом можно было поднять число итераций или перейти на Argon2id (через WASM) с миграцией при следующей разблокировке. Время PBKDF2 на iPhone замеряется на этапе 0.

### 5.2. Формат зашифрованного конверта (для всех `.enc`)

```
┌────────┬──────────┬───────────┬───────────────────────────────┐
│ magic  │ version  │ IV (12 B) │ ciphertext + GCM tag (16 B)    │
│ "KTS1" │ 1 byte   │ random    │                                 │
└────────┴──────────┴───────────┴───────────────────────────────┘
AAD (дополнительные аутентифицируемые данные) = `${vaultId}|${kind}|${objectId}|${rev}`
```

- **IV** всегда случайный (crypto.getRandomValues) и никогда не повторяется для одного ключа.
- **AAD** привязывает шифротекст к месту: нельзя подменить файл одного шарда файлом другого или незаметно откатить ревизию.
- **Перед шифрованием** открытый JSON сжимается (fflate deflate). Фото не сжимаются повторно.
- **Паддинг длины:** шарды дополняются до ближайшего кратного 4 КБ.

### 5.3. `vault.json` (единственный открытый файл)

```json
{
  "format": "ketsal-vault",
  "version": 1,
  "vaultId": "01J…",
  "createdAt": "2026-09-25T12:00:00Z",
  "kdf": { "alg": "PBKDF2-SHA256", "iterations": 600000, "salt": "base64…" },
  "wrappedDek": {
    "password": { "iv": "…", "ct": "…" },
    "recovery": { "iv": "…", "ct": "…", "hkdfSalt": "…" }
  },
  "verifier": { "env": "base64 конверта KTS1…" }
}
```

`verifier` — известная строка, зашифрованная DEK в конверте §5.2 (AAD `vaultId|verifier|vault|1`): подтверждает, что развёрнут верный ключ. Секретов в `vault.json` нет. Пароль перед PBKDF2 нормализуется в NFC.

### 5.4. Сессия и блокировка

- **DEK хранится только в памяти** как `CryptoKey` с `extractable: false`.
- **Автоблокировка** через N минут бездействия и при `visibilitychange → hidden` дольше 60 секунд. После блокировки ключ и расшифрованные данные удаляются из памяти, objectURL‑ы отзываются. Незаконченная форма после разблокировки не восстанавливается (черновик не хранится открытым).
- **Быстрая разблокировка** (этап 6; выбирается при первом запуске и в настройках):
  - **Face ID через passkey (WebAuthn PRF).** Если браузер поддерживает PRF, из passkey выводится ключ, который оборачивает DEK. Поддержка проверяется на этапе 0 и при запуске; нет поддержки — опция не показывается.
  - **Код из 6 цифр.** DEK оборачивается ключом из `PBKDF2(PIN)` в сочетании с неизвлекаемым ключом устройства в IndexedDB. После 5 неверных попыток обёртка стирается и нужен мастер‑пароль. В интерфейсе честно сказано, что код слабее пароля.
  - **Только мастер‑пароль.**
- При первом запуске вызываем `navigator.storage.persist()`.

### 5.5. Модель угроз (коротко)

| Угроза | Защита |
|---|---|
| Яндекс или взломщик аккаунта Яндекса читает данные | E2E, на Диске только шифротекст |
| Подмена или откат файлов на Диске | AAD с ревизией + монотонные ревизии в каталоге; расшифровка падает, пользователь видит предупреждение |
| Кража разблокированного телефона | Автоблокировка, быстрая разблокировка только по биометрии или коду с лимитом |
| Доступ к файлам браузера на ПК | IndexedDB содержит только шифротекст |
| Подмена JS на хостинге | Строгий CSP, никаких внешних скриптов, SW обновляется только после подтверждения пользователя. **Полностью не решается** — ограничение любого веб‑приложения, фиксируем в README |
| Утечка геолокации через фото | EXIF удаляется при обработке (перерисовка через canvas) |
| Забытый пароль | Ключ восстановления; без него данные невосстановимы (намеренно) |
| Удаление данных на Диске | Локальная копия + регулярные бэкапы + напоминание |

## 6. Хранилище на Яндекс Диске

### 6.1. Доступ

- **Приложение регистрирует салон** на oauth.yandex.ru под своим Яндекс ID. Права: только **«Доступ к папке приложения на Диске»** (`cloud_api:disk.app_folder`). Остальной Диск приложение не видит. ClientID публичный и хранится в конфиге сборки; client secret в браузер не попадает.
- **Redirect URI:** `https://voa-app.github.io/ketsal-crm/` (приложение), `https://voa-app.github.io/ketsal-crm/spikes/` (проверки этапа 0), `http://localhost:5173/` и `http://localhost:5173/spikes/` (разработка).
- **Поток авторизации:** OAuth 2.0 Authorization Code + **PKCE** без client secret, переход на oauth.yandex.ru в том же окне. Этап 0 (25.10.2026): обмен кода на токен из браузера работает, вход с экрана «Домой» возвращается в «Домой»; токен живёт ≈ 365 дней, есть refresh_token. Запасные потоки не нужны.
- **Токен хранится** в IndexedDB, зашифрованный неизвлекаемым ключом устройства: он нужен до разблокировки, чтобы скачать `vault.json`. При ответе 401 — повторная авторизация.

### 6.2. Раскладка файлов (`app:/` = `Приложения/<название приложения>/`)

```
app:/
├─ vault.json                       ← открытый заголовок (§5.3)
├─ catalog.enc                      ← настройки, списки + таблица ревизий шардов
├─ shards/
│  ├─ 00-17-a1b2c3.enc …            ← записи (конверты §4.1): <шард>-<ревизия>-<устройство>.enc
├─ blobs/
│  ├─ 01J9…Q.enc                    ← фото (случайные имена)
│  └─ …
└─ thumbs/
   └─ 01J9…R.enc                    ← превью 400px
```

`catalog.enc` содержит `catalogRev`, ссылки на действующие файлы шардов `shardFiles: { "00": { rev: 17, file: "00-17-a1b2c3.enc" }, … }`, настройки и списки плоскими ключами (`settings.corrFrom`, `lists.tags`) с отметками времени по полям.

**Уточнение этапа 3 (27.10.2026).** У каждой версии шарда своё имя файла, а не `00.enc`: у Яндекс Диска нет условной записи («записать, только если файл не изменился»), и при одновременной синхронизации двух устройств одна запись могла бы молча затереть другую. Теперь чужая версия видна по новому имени файла: устройство скачивает её, сливает со своими данными и отправляет недостающее. Старые версии удаляются, когда отстают от действующей больше чем на 2 ревизии.

Файл на Диске: 4 байта ревизии (big-endian) + конверт §5.2; ревизия входит и в AAD, поэтому подменить её нельзя.

### 6.3. Интерфейс адаптера

```ts
interface StorageAdapter {
  getMeta(path: string): Promise<{ etag?: string; size: number; modified: string } | null>;
  read(path: string): Promise<Uint8Array | null>;
  write(path: string, data: Uint8Array): Promise<void>;   // overwrite
  remove(path: string): Promise<void>;
  list(dir: string): Promise<{ name: string; size: number; modified: string }[]>;
}
```

`YandexDiskAdapter` реализует его через REST API Диска: `GET /v1/disk/resources`, `GET …/download` → href → GET, `GET …/upload?overwrite=true` → href → PUT, `DELETE`.

**GET по href скачивания — только с `referrerPolicy: 'no-referrer'`** (этап 0, 25.10.2026): с Referer чужого сайта `downloader.disk.yandex.ru` отвечает 403 без CORS, без Referer отдаёт файл (с перенаправлением на `*.storage.yandex.net`).

### 6.4. ⚠️ Главный технический риск: CORS

Нужно проверить, отдают ли **ссылки на скачивание и загрузку** Диска заголовки CORS для прямых запросов из браузера. Это же касается `oauth.yandex.ru/token`. Проверка — **этап 0** (`spikes/index.html`).

**Запасной вариант, если CORS нет:** прокси‑функция в **Yandex Cloud Functions**: принимает запрос с токеном и пересылает байты на Диск и обратно. Данные идут через неё уже зашифрованными. Бесплатного уровня хватает с запасом; нужен платёжный аккаунт Yandex Cloud с привязанной картой. Архитектура от этого не меняется: появляется `ProxyAdapter` с тем же интерфейсом.

## 7. Синхронизация

### 7.1. Часы и слияние

- У каждого изменения есть **HLC‑метка** (физическое время + счётчик + deviceId).
- **Слияние пополевое, LWW:** для каждого поля верхнего уровня `v` побеждает значение с большей HLC из `fieldUpdatedAt`. Если на телефоне поменяли стоимость, а на компьютере статус, сохранятся оба изменения.
- **Удаление** оставляет tombstone `deleted: true`. Удаление окончательно: правка той же записи с другого устройства его не отменяет (иначе слияние перестаёт быть ассоциативным и устройства могут разойтись). «Вернуть» сразу после удаления создаёт запись заново под новым id. Компактизация tombstone старше 90 дней — позже, вместе с нагрузочным тестом (этап 7).
- **Полное удаление клиента (§1.3)** оставляет tombstone `{ id, kind, deleted: true, purged: true, updatedAt }` без `v` у клиента и у каждой его процедуры. `purged` побеждает любые правки независимо от HLC.
- **Каталог** (настройки, списки) сливается так же, пополевно; `nextCardNo` и `nextCertNo` — по максимуму.
- **Номер карты при одновременном создании на двух устройствах** может совпасть: после слияния дубль получает следующий свободный номер, в карте — отметка «номер изменён при синхронизации».
- **Слияние детерминированно и коммутативно:** merge(A,B) = merge(B,A). На это пишутся property‑тесты.

### 7.2. Цикл синхронизации

```
1. pull catalog.enc  → расшифровать → если catalogRev меньше последнего виденного
   этим устройством — стоп, предупреждение «возможен откат данных на Диске»;
   иначе слить с локальным каталогом
2. для каждого шарда, где remote.rev > local.rev:
      скачать → расшифровать → слить с локальным шардом
3. применить outbox (локальные изменения) — они уже в локальных шардах
4. для каждого «грязного» шарда: rev = max(local, remote) + 1 → зашифровать → PUT
5. загрузить новые blobs/thumbs (ещё не synced)
6. PUT catalog.enc с новыми ревизиями
7. повторно прочитать catalog.enc; если чужая ревизия выше ожидаемой — повторить с шага 1
   (максимум 3 попытки)
8. сборка мусора: blob‑файлы, на которые нет ссылок > 7 дней → удалить
```

- **Когда запускается:** при старте, при возврате в приложение (`visibilitychange`), через 3 секунды после последнего изменения, по кнопке и при появлении сети.
- **Индикатор в UI:** «Синхронизировано · 2 мин назад» / «Нет сети, изменения сохранены» / «Ошибка → подробнее».
- **Фото загружаются** отдельной очередью, с повторами и экспоненциальной задержкой. Оригиналы скачиваются лениво, превью — сразу.

## 8. Фото

```ts
interface PhotoRef {
  blobId: ID;            // случайный ID, не связан с содержимым
  thumbId: ID;
  width: number; height: number;
  bytes: number;
  takenAt?: string;      // дата съёмки из EXIF, прочитанная ДО удаления EXIF (по настройке)
}
```

1. Выбор: `<input type="file" accept="image/*" multiple>` (камера или галерея).
2. Декодирование через `createImageBitmap` (на iPhone снимки камеры открываются, этап 0), fallback через `<img>`.
3. Если включено `keepTakenAt`, до перерисовки из EXIF читается **только** дата съёмки.
4. Ресайз до `photoMaxSide` (2560 px) через `OffscreenCanvas` или canvas, JPEG 0.85. **Перерисовка удаляет весь EXIF, включая GPS.**
5. Превью: 400 px, JPEG 0.75.
6. Оба файла шифруются DEK с AAD `…|photo|blobId|1`, сохраняются в IndexedDB (`synced: false`), затем отправляются на Диск.
7. Показ: превью расшифровывается → `Blob` → `URL.createObjectURL` → LRU‑кэш на ~200 штук, освобождение через `revokeObjectURL`.

Подписи к фото — «До», «Сразу после», «Через месяц»; текст на фото не накладывается (правило брендбука).

**Фото на Диске (уточнение этапа 4, 27.10.2026):**
- Файлы `blobs/<blobId>.enc` и `thumbs/<thumbId>.enc` — тот же конверт, что в IndexedDB (AAD `…|photo|<id>|1`), без перешифрования.
- Фото идут отдельной очередью после синхронизации записей: загружается только фото, на которое уже есть ссылка в данных (фото незакрытой формы ждут). При ошибке — повтор через 10 с, 20 с, 40 с … до 5 минут.
- Превью скачиваются сразу после синхронизации, оригинал — при первом открытии; пока он грузится, видно превью. Файл, который не расшифровался своим ключом и своим id, не принимается.
- Фото убрали из карты или процедуры, удалили процедуру или карту полностью — файлы удаляются с Диска при следующей синхронизации; не загруженные туда — только с устройства.
- Уборка: с устройства — файлы без ссылок в данных старше 10 минут (кроме фото открытых форм); с Диска — файлы без ссылок старше 7 дней, не чаще раза в сутки.
- Ограничение: фото процедуры — одно поле `photos`. Если одновременно без сети добавить фото к одной и той же процедуре на двух устройствах, после синхронизации останутся фото только одного из них.

## 9. Экспорт и импорт

### 9.1. Зашифрованный бэкап `.ketsal`

- **Формат:** ZIP без сжатия (fflate) с той же раскладкой, что на Диске, плюс `manifest.json` с SHA‑256 каждого файла.
- **Экспорт:** всё собирается из IndexedDB, недостающие оригиналы фото сначала докачиваются. Сохранение: на iPhone через `navigator.share({ files })` («Сохранить в Файлы», Телеграм), на ПК через `<a download>`.
- **Импорт:** выбрать файл → проверить manifest и хэши → пароль или ключ восстановления бэкапа → «Заменить всё» (двойное подтверждение) или «Объединить» (слияние по §7.1; при другом `vaultId` — перешифровка текущим DEK).
- **Напоминание о бэкапе:** если последний был больше `backupReminderDays` дней назад — баннер в списке клиентов.

**Уточнения этапа 5 (27.10.2026):**
- ZIP пишется и читается своим кодом (`backup/zip.ts`, без сжатия, CRC-32, имена в UTF-8), а не `zipSync` из fflate: копия с фото может весить сотни мегабайт, а на iPhone мало памяти. Части складываются в `Blob`, при чтении файлы берутся по одному через `Blob.slice`. Совместимость с fflate проверяется тестом.
- Шарды в копии — `shards/<шард>-1-backup.enc`, вместе с удалёнными записями (tombstone), каталог — ревизия 1. Фото — те же конверты, что в IndexedDB.
- Копию этого же хранилища открывает текущий ключ, без пароля. Копию другого хранилища — её пароль или ключ восстановления; фото перешифровываются текущим ключом.
- «Объединить» — слияние по §7.1 (в том числе дубль номера карты). «Заменить всё» — данные становятся как в копии и с новыми отметками времени уходят на другие устройства; ввод слова «заменить».
- Записи, удалённые на устройстве после копии, из неё не возвращаются ни в одном режиме: удаление окончательно (§7.1), а полное удаление (§1.3) не должно отменяться копией.
- Сохранение: на телефоне — «Поделиться» («Сохранить в Файлы», Телеграм), на ПК — загрузкой. Для долгой сборки (копия, архив с фото) кнопка сохранения — вторым нажатием: Safari разрешает «Поделиться» только из нажатия.

### 9.2. Открытый экспорт

- CSV (UTF‑8 с BOM, разделитель `;`): клиенты, процедуры, расходники; фото — отдельной папкой в ZIP (архив «Всё с фото»: три таблицы и `Фото/<№ карты ФИО>/<дата зона стадия N>.jpg`). Текст, начинающийся с `= + - @`, экранируется, чтобы Excel не выполнил его как формулу.
- Перед выгрузкой — **обязательное предупреждение**: «Файл не зашифрован и содержит персональные данные клиентов…».
- Данные о здоровье по умолчанию **не включаются**; для них отдельная галочка.
- **Карта одного клиента** — печать / PDF (материалы, фото, здоровье — по галочкам), как в прототипе.

### 9.3. Импорт существующей базы

Не нужен: старой базы нет (решено).

## 10. Интерфейс

### 10.1. Навигация и экраны (как в прототипе)

- **Таб‑бар:** Клиенты · Процедуры · Справочники · Ещё. На «Клиентах» — значок с числом коррекций к напоминанию.
- **Клиенты:** крупный заголовок, поиск, лента видов (Все, Коррекция, Обновление, Именинники, Модели, Давно не были, Без согласия) со счётчиками, сортировка (фамилия, номер карты, последний визит), баннер о бэкапе, кнопка «+» (новая карта).
- **Карта клиента:** шапка с именем, телефоном, метками и кнопками «Позвонить», «Написать», «PDF»; карточки напоминаний с «Повторить как в прошлый раз»; итоги; вкладки «История», «Фото» (по зонам, сравнение «до» и «через месяц»), «Данные» (контакты, согласия, анкета под «Показать», итоги, печать, полное удаление); нижняя кнопка «+ Процедура».
- **Форма процедуры** — нижняя шторка, порядок полей как в прототипе; «Сохранить и добавить ещё одну зону».
- **Процедуры:** журнал по дням с итогом периода (сегодня, 7 дней, этот месяц, прошлый, все), поиск по клиенту, услуге, пигменту и партии; карточка процедуры с быстрым добавлением фото и заживлением; удаление с «Вернуть».
- **Справочники:** услуги, пигменты (партии и сроки), иглы, анестезия (действующие вещества), зоны (техники, напоминание об обновлении), курсы. Используемое не удаляется, а убирается из выбора.
- **Ещё:** синхронизация, отчёты, расходники, сертификаты, резервная копия и выгрузка, настройки, заблокировать.
- **Главный сценарий (≤ 3 тапа до начала ввода):** «Клиенты» → поиск → карта → «Повторить как в прошлый раз» или «+ Процедура».
- **Сообщения:** шаблон → копирование → отметка «напомнили». Звонок — `tel:`, мессенджер — ссылка на профиль (без подстановки текста в URL).

### 10.2. Визуальный стиль

- **Брендбук «Кетсаль»:** изумруд `#217870`, глубокий изумруд `#14514B`, мятный `#E7F0EE`, молочный `#F7F4F0`, графит `#2B2223`, серый `#6E7674`, линия `#DFE4E2`, алый `#D00405` — только маркеры‑точки и число на значке. Изумруда не больше четверти экрана.
- **Шрифты:** Onest (400/500/600) — интерфейс; Cormorant Garamond (300/400) — крупные заголовки, **только от 24 px**. Оба сабсета (latin + cyrillic) с unicode‑range, иначе пропадут цифры.
- **Логотип** — на экране входа и в печатной карте, не меньше 160 px по ширине, с охранным полем 40 % высоты. Силуэт птицы — один, с уходом за край. Латиница QUETZAL не используется нигде.
- **Светлая и тёмная темы** по `prefers-color-scheme` и ручной переключатель.
- **Учёт выреза и home indicator:** `viewport-fit=cover` + `env(safe-area-inset-*)`. Тач‑цели не меньше 44×44 pt, у инпутов `font-size` ≥ 16px. Анимации ≤ 250 мс, отключаются при `prefers-reduced-motion`.
- **Мета‑теги** `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-touch-icon` (птица на изумруде из брендбука), splash‑экраны.
- **Весь текст на русском** в `i18n/ru.ts`. Без капса и восклицательных знаков в интерфейсе.

### 10.3. Онбординг (первый запуск)

Как в прототипе: приветствие с инструкцией «На экран Домой» → «Войти через Яндекс» → мастер‑пароль с индикатором надёжности → ключ восстановления → проверка 4 символов → быстрый вход (Face ID, код, только пароль) → готово. Если хранилище уже есть — пароль и первая синхронизация.

## 11. Хостинг и безопасность доставки кода

- **GitHub Pages (решено).** Репозиторий `ketsal-crm` открытый: в нём только код, данных клиентов нет. Деплой через GitHub Actions (`.github/workflows/pages.yml`). Свой домен — по желанию.

  ```
  default-src 'self';
  script-src 'self';
  style-src 'self';
  font-src 'self';
  img-src 'self' blob: data:;
  connect-src 'self' https://cloud-api.yandex.net https://oauth.yandex.ru https://*.disk.yandex.net https://*.disk.yandex.ru https://*.storage.yandex.net;
  worker-src 'self';
  base-uri 'none';
  form-action 'none';
  ```
  Точный список `connect-src` — по хостам из `spikes/RESULTS.md`. `frame-ancestors` в meta не работает; на GitHub Pages защита от встраивания — через `if (window.top !== window.self)` → пустой экран.
- **Service Worker:** precache всех ассетов. Новая версия **не** активируется молча: «Доступно обновление → Обновить».
- **`<meta name="referrer" content="no-referrer">`** на всё приложение: адрес страницы не уходит на чужие хосты, и скачивание с Диска работает (§6.3).
- **Сборка без source maps.** Версия и хэш коммита видны в «Ещё → О приложении».
